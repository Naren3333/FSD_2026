# Learning Ledger interaction contract

Business authority: docs/requirements.md sections 6, 8, 15–18 and docs/decisions/0001-foundation.md. Teachers own their classrooms. Students submit once; grades are immutable after teacher finalization. All authorization remains server-enforced.

| Capability | Canonical owner | Source of truth | Allowed variants | Verification |
|---|---|---|---|---|
| Form | shared field component + Reactive Forms | this contract | create, submit, review | Angular tests + browser E2E |
| Select/Listbox | native select | DESIGN.md | classroom, topic, type | keyboard/browser |
| Scrollbar | global styles.css | DESIGN.md | document and horizontal tables | static + browser |
| Toast | shared status component | this contract | status, error | unit + browser |
| CRUD | feature components + Api service | API/domain contracts | create, refresh list, edit/publish/delete draft, mark, release, remove enrollment, delete classroom, archive curriculum | live E2E |

Creation retains the owning view, refreshes the real list, clears only successfully saved input, and announces completion. Validation keeps entered values and focuses the first invalid control. Mutations disable their submit button. Failed operations retain input, explain the failure, and allow explicit retry; no automatic mutation retries. Authentication failures offer sign-in without deleting drafts. Tokens remain in memory through Keycloak JS; on load the app asks Keycloak, without showing its login page, whether the browser is still signed in, so a refresh keeps the user signed in. While a signed-in user's profile loads, the workspace shows a loading state, never the signed-out welcome; if it fails to load, it explains why and offers Try again and Sign out.

Tab panels stay mounted to retain work; page unload warns when a form is dirty. Classroom context changes are disabled while work is unsaved. Finalization uses an explicit review reason and an app-owned confirmation dialog; cancel is the initially focused action. Removing a student from a classroom uses the same app-owned confirmation dialog with Cancel focused; it keeps their submissions and grades and is undone by enrolling them again. Deleting a classroom uses the same dialog with Cancel focused; it ends everyone's access, unenrolls its students (their accounts are kept) and purges the classroom's materials, assessments, submissions, grades, performance evidence and chat threads in every service. It cannot be undone. Deleting a draft assessment uses the same dialog with Cancel focused; published assessments have no delete. Releasing an assessment's results uses the same dialog and cannot be undone. Archiving a curriculum topic uses the same dialog with Cancel focused; it hides the topic from every list and new questions and deletes nothing (existing assessments and evidence keep it, shown by its id). No other delete UI in this milestone.

Assessments are drafts until published; the editor keeps unsaved work and warns on unload, and students never see drafts. Students' answers are saved as they type (the result is announced politely, a failure keeps the answers), past-due and closed states are explained in words, and written answers show a character count. In Grading review, questions waiting for the teacher are counted on each grade; marking happens inline with rubric levels as radio groups, points and optional feedback; finalizing with a question unmarked keeps the input and focuses the first missing mark. AI suggestions are labelled as AI-written, show the student's quoted words, and change nothing until the teacher chooses "Use suggestion" and then saves or finalizes. In the editor, short-answer and written-response questions take up to five marking-scheme passages: the teacher searches one indexed marking scheme or rubric of the classroom with the question's wording and adds passages from the results, or pastes one; loading, no-scheme, no-match and failed-search states are explained in place and the passages already added are kept. A suggestion says how many passages it read and shows them; students never see passages. Teachers can also have AI draft questions from chosen teaching materials ("Generate questions"), draft accepted answers or a rubric and marking points for a question they wrote ("Draft marking guidance"), and add the best passage of one marking scheme to each teacher-marked question ("Match scheme to questions"). Each explains its loading, no-document and failure states in place, labels its output as AI-written with the passages it came from, and changes nothing until the teacher adds a draft or chooses "Use this"; guidance for a question that was reworded since is not used. Keeping or discarding a draft moves focus to the next draft, or back to Generate. The per-question and per-assessment passage limits hold for all three; marking points that do not fit are left out and said so. Marking points the model wrote are labelled as AI-written while the editor is open and pasted ones as pasted (after a reload both read "Written passage, not from a document"); generating and drafting spend the teacher's daily AI allowance.

Lists are capped by APIs at 100 (curriculum 200); the UI states this limit. The school's students and the class dashboard's topics table are paged on the server (ten and twenty at a time) with Previous/Next controls; other lists are not yet paged. No search or selection feature is claimed. Empty states explain the next action. All shared feedback reserves space. Errors appear inline; status has a polite live region.

Unsupported AI actions are explanatory text with disabled controls. PDFs show their indexing status (indexing, indexed with page and passage counts, or failed with a reason and a teacher-only retry); text files say they are not indexed. Chat questions stay in the field until the chatbot accepts them, answers stream with a Stop control, every answer ends answered, with no matching material, failed or stopped, and failures appear inline with the question kept for retry. Answers render the model's Markdown subset (paragraphs, lists, headings, bold, italic, code) as text, never as HTML; each source shows the whole passage the model was given, its page range, and a control that opens the original PDF at its first page. Displayed metrics come only from finalized evidence. The teacher's Class dashboard loads each of its parts (grading counts, roster, submissions, class topics) on its own, so one failing service shows its error in place while the rest still load; each part has its loading and empty state, and the topics table scrolls sideways on narrow screens. The student's Home does the same for their to-do list, recent results and topics to practise; its waiting-for-review count is derived from their own submitted assessments and finalized results, never from draft grades. Dates/numbers use en-SG; people, assessments, questions and topics are shown by the names their owning services return; an id is shown, as a plain identifier, only when no name exists.
