# Operations and recovery

Compose refuses to start while `.env` lacks a value it requires ("Run scripts/setup.py or scripts/upgrade_local.py"). `python scripts/upgrade_local.py` (`make upgrade_local`) appends every value `setup.py` would generate that `.env` lacks and never changes an existing line; with the stack up it also creates missing databases and Keycloak clients. `POSTGRES_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD` and the local people's passwords are read only when their volume is first created, so adding them to an old `.env` does not change a running stack's existing passwords.

## Upgrading a local setup made before ADR 0002

`scripts/setup.py` now also generates the AI service-account secrets (`CONTENT_INDEXER_CLIENT_SECRET`, `QUESTION_CHATBOT_AGENT_CLIENT_SECRET`), adds their Keycloak clients to the realm, and creates the `vector` extension in Content's database. It never overwrites an existing `.env`, and Keycloak and Postgres only import on an empty volume.

If you have no local data you want to keep, back up `.env`, then run `docker compose down -v`, delete `.env` and `.local/`, rerun `python scripts/setup.py`, and run `docker compose up -d --build`. **This deletes every local database, upload and Keycloak user.**

Document storage moved from MinIO to SeaweedFS (volume `seaweedfs-data`). Documents in an old `minio-data` volume are not migrated; re-upload them, or copy them out with any S3 client before removing that volume.

ai-core reads `OPENAI_API_KEY` and `VOYAGE_API_KEY` from `.env`. A new setup writes them empty; an older `.env` needs the two lines added by hand. Without them ai-core starts and answers `503 AI_PROVIDER_NOT_CONFIGURED`, and the integration test accepts that.

The chatbot (stage 4) has its own database: run `python scripts/upgrade_local.py` once with the stack up. It adds `CHATBOT_DB_PASSWORD` to `.env` and creates the `chatbot` role and database, changing nothing that exists. Then `docker compose up -d --build` and `docker compose restart kong` (new `/api/chatbot` route).

Content indexing (stage 3) needs no reset: Content's migration `002_indexing.sql` applies on start and keeps existing documents. Run `docker compose up -d --build`, then `docker compose restart kong` so Kong loads the larger Content body limit; `kafka-init` creates the new `content.indexed.v1` topic.

The Postgres image also changed from Alpine to Debian (pgvector), so text-index collations differ. Recreating the volume is the clean path. Keeping data means reindexing every database (`REINDEX DATABASE <name>;` as each owner) after the switch, plus adding the clients and extension by hand.

## Assessment lifecycle and AI marking (ADR 0004)

An existing local setup needs one upgrade: `python scripts/upgrade_local.py` adds `GRADING_MARKER_CLIENT_SECRET` to `.env`, creates the `grading-marker` client in the running Keycloak (its service account gets `ai-client`), and rewrites `.local/learning-realm.json` so a fresh Keycloak volume has it too. Then `docker compose up -d --build` (Assessment, Grading and Analytics migrations apply on start and keep existing data; `kafka-init` creates `assessment.submitted.v2`, `grading.finalized.v2` and their `.dlq` topics) and `docker compose restart kong` (CORS now allows `PUT`). Grading will not start without the new secret, so when the stack is down the script adds the secret and stops; start the stack, wait for `python scripts/wait_ready.py`, run the script again, then `docker compose restart grading`.

Pending AI suggestions are in Grading's `marking_jobs` table: `attempts`, `run_after` and `last_error` explain a waiting one, for example `AI_PROVIDER_NOT_CONFIGURED` until provider keys are set or `AI_SPEND_LIMIT` until the teacher's allowance resets. `AI_PROVIDER_NOT_CONFIGURED` keeps the suggestion pending and retries every 10 minutes without using an attempt; `AI_OUTPUT_REJECTED` (a reply ai-core refused) is not retried. A suggestion stops with `MARKED_BY_TEACHER` once the teacher marks the question by hand, and `MARKING_INTERRUPTED` when its job could not finish. A job is deleted when its suggestion is stored or the grade is finalized. Suggestions never change a mark, so a stuck job only means the teacher marks that question without help.

A manual-release assessment's finalized grades reach students, and Analytics, only when the teacher releases them: `grading.finalized.v2` is written to Grading's outbox in the release's transaction. An assessment that releases on finalization writes it at finalization.

## Test students

`python scripts/seed_students.py` adds thirty local test students (aisha.rahman, ben.tan and so on) to the Keycloak realm and signs each in once so a teacher can enroll them by username. They share one generated password, printed at the end and kept in `.local/seed-students.json`. Re-running keeps them and their password.

## Health and logs

Each application exposes `/health/live` and `/health/ready` on its private port 8080. Persistent apps check PostgreSQL; Content also checks the document bucket; Grading marks readiness unavailable after its consumer stops; Analytics and the chatbot check only their database, because their consumers restart themselves and a broker outage only delays new evidence or purges (watch for `consumer_stopped_uncommitted` and `consumer_restarting` in their logs). The two AI placeholders (question generation and performance interpretation) need only valid authentication configuration; the chatbot also checks its database. ai-core's readiness reports whether the OpenAI and Voyage keys are set, without calling either (a paid probe on every check would cost money and latency); a provider outage shows per request as `502 AI_PROVIDER_FAILED`.

ai-core keeps one disk cache, the `ai-core-cache` volume: vision-model answers keyed by page content, model and prompt version, so re-indexing an unchanged document makes no vision calls. It holds no business records and can be deleted at any time; the next ingest repopulates it at the cost of new model calls. A readiness probe is a dependency snapshot, not proof of fresh analytical results.

Go uses JSON slog and Python emits JSON application telemetry. Request IDs and correlation IDs are returned in headers; correlation IDs flow across authorization HTTP requests and event envelopes. Tokens, bodies and student answers are not logged. Third-party server/broker startup diagnostics may use their own format. Extend these boundaries with OpenTelemetry HTTP/Kafka propagation and trace exporters in a later milestone; no tracing collector is installed.


## Content indexing

PDF uploads are indexed by Content's worker through ai-core. A document's `status` shows the state: `indexing`, `indexed`, or `failed` with `failure_reason` (`NO_TEXT_LAYER`, `ENCRYPTED`, `CORRUPT` from the PDF itself; `TOO_LARGE` for a PDF over ai-core's `INGEST_MAX_PAGES` (500) pages or `INGEST_MAX_CHUNKS` (5000) chunks, refused before the model calls they would cost; `AI_UNAVAILABLE` after six failed attempts to reach ai-core or its providers; `INTERNAL` for a result Content could not store). Pending work is in Content's `index_jobs` table: `attempts`, `next_attempt` and `last_error` explain a waiting job, for example `ai-core 503 AI_PROVIDER_NOT_CONFIGURED` until provider keys are set. After fixing the cause, a teacher (or `POST /v1/documents/{id}/reindex`) queues the document again; PDFs uploaded before indexing existed (`extraction_unsupported`) are indexed the same way. Each ingest costs model calls, so do not loop reindexes.

`python scripts/db_tests.py` (`make db_tests`) runs the database-backed tests that `check.py` skips (it has no database, and lists them as not run). Each Go module's tests run in a Go container: the platform outbox, consumer inbox and migrations, and the Identity, Curriculum, Assessment, Grading and Content stores (Content with pgvector). The Python ones run in each service's own image: ai-core's usage ledger, Analytics' consumer SQL and the chatbot's PostgresStore. All run on the Compose network. The script creates a scratch `<name>_test` database per suite once, owned by a service's role, and every test works in a throwaway schema of it, so no service's real data is touched. Each suite reads its URL from `<NAME>_TEST_DATABASE_URL` (for example `GRADING_TEST_DATABASE_URL`; Go tests use `platformtest.DB`). The script fails if a suite skips instead of running. To run one suite by hand, point that variable at any PostgreSQL 17 with pgvector and run `go test ./...` or `pytest` in the module.
## AI spend caps (ADR 0003)

Every paid model call is charged to a user in ai-core's `aicore` database (`usage` table: user, operation, model, tokens, cost, and whether the tokens were estimated). Chat turns and searches are charged to the user who made them; indexing a PDF is charged to the teacher who uploaded it. Once a user's spend since midnight (`SPEND_TIMEZONE`, default Asia/Singapore) reaches `SPEND_LIMIT_STUDENT_USD` (5) or `SPEND_LIMIT_TEACHER_USD` (10), ai-core answers `429 AI_SPEND_LIMIT` before calling any provider: the chat turn ends with that error and the reset time, search answers 429, and an index job waits until the reset without using a retry. Users see their spend in the web app's header (the chatbot's `GET /v1/usage`). Because the check comes before a call and the charge after it, calls already running can take a user past the limit; ai-core therefore lets one user run at most `AI_USER_CONCURRENCY` (default 4, counted per ai-core process) inference and rerank calls at once and answers `429 AI_BUSY` past that. A chat turn ends with that error, search answers 429 `AI_BUSY` (a failed rerank falls back to fused order instead), and a marking job waits 30 seconds without using a retry. PDF ingests are not counted: they already queue for ai-core's two ingest slots and re-check the allowance when they get one.

Prices live in `services/ai-core/spend.py` (USD per million tokens). Check them against OpenAI's and Voyage's price pages when a model or price changes, or override them with `MODEL_PRICES`, a JSON object of `{"model": [input, cached_input, output]}`. To see what a user spent: `SELECT date_trunc('day', created_at AT TIME ZONE 'Asia/Singapore') AS day, sum(cost_usd) FROM usage WHERE user_id='<sub>' GROUP BY 1 ORDER BY 1 DESC;` as the `aicore` role. If the ledger is down, ai-core reports not ready and refuses paid calls with `503 USAGE_LEDGER_UNAVAILABLE`.

An existing local setup needs the new database once: `python scripts/upgrade_local.py` with the stack up, then `docker compose up -d --build`.

## Chatbot

A chat turn needs Content, ai-core with an OpenAI key, and (for reranking) a Voyage key. Without a key the turn ends with an `AI_UNAVAILABLE` error event and the message is saved with outcome `error`; without Voyage, search falls back to RRF order, which the relevance floor cannot check, so the turn ends with a `SEARCH_UNAVAILABLE` error instead of an answer. `RELEVANCE_FLOOR` (default 0.61, fsd_test's tuned value for Voyage rerank scores) and `ANSWER_MAX_TOKENS` (800) are optional environment settings. Each saved answer records its rewritten query, the chunk ids it was given, its citations, prompt version, model, tokens and latency, which is what to look at when an answer is wrong. The Postgres store tests run with `CHATBOT_TEST_DATABASE_URL` pointing at a scratch database; `scripts/db_tests.py` sets that up. Every thread read and turn re-checks classroom access at Identity, so a student removed from a classroom can no longer open its threads.

## Retrieval eval (golden set)

`scripts/eval/` scores Content's search through Kong as real local users, with fsd_test's golden queries plus later batches (`golden.yaml`, 290 queries) and the same scoring, so results compare with fsd_test's runs. The test PDFs are course material and are not in this repository: they are read from `EVAL_PDF_DIR` (default `../fsd_test/data/test_pdfs`), as listed in `corpus.yaml`.

1. `python scripts/eval/load_corpus.py` creates the classrooms "Golden eval C1" and "Golden eval C2" as `teacher`, enrolls `student` in C1, creates a second local test student `eval-student2` for C2 (its generated password and the classroom and document ids are kept in `.local/eval-corpus.json`), uploads the PDFs and waits for indexing. It is safe to re-run.
2. `python scripts/eval/run_golden.py --rerank --holdout [--label NAME] [--compare .local/eval-runs/EARLIER.json]` prints hit@1/3/5, MRR, recall, leaks and the refusal-floor table, including where the chatbot's `RELEVANCE_FLOOR` 0.61 falls. It exits 1 on a leak. Runs are saved in `.local/eval-runs/`.

Costs: indexing pays for embeddings and for vision calls on pages ai-core has not cached (copying fsd_test's `data/table_vision/` into ai-core's cache volume under `vision/`, owned by uid 10001, makes the vision pass free); each eval query pays one embedding and one Voyage rerank per classroom searched. Teacher queries search both classrooms and keep the best-scoring results, because search is per classroom. Queries with a `topic_ids` filter are skipped: Content has no topics.

Baseline (2026-10-13, `rerank-3`, all 266 runnable queries): hit@1 0.959, hit@3 0.991, MRR 0.975, recall@5 0.962, 0 leaks; held-back split MRR 0.967. The best refusal floor is 0.613, which refuses 93% of unanswerable queries and keeps 96% of correct answers. These match fsd_test's run on the same queries. A later batch of 23 questions phrased away from the slides' wording (`off-*`) scores lower, MRR 0.91 on its 18 answerable ones, and all 5 of its unanswerable ones are refused; with it the set has 290 queries and MRR 0.971.

`python scripts/eval/run_chat.py [--only GROUP] [--label NAME]` runs real chat turns through Kong in the same classrooms: 96 cases in 100 turns. Groups: `refusal` (golden's unanswerable queries), `leaks` (students asking for rubric, marking-scheme or other-class content), `grounded` (golden questions that must be answered with a citation on an expected page), `followup`, `injection` (instructions planted in documents or typed by the user), `rubric` (teachers answered from teacher-only documents) and `socratic` (transcripts to read). It reads what the API doesn't return, such as the chunks a turn retrieved, from the chatbot's and Content's local databases. It exits 1 on an error, a leak, a citation that wasn't retrieved, an obeyed injection, or a grounded answer that cites none of the expected pages. Every turn costs model calls: the first run used about 91,000 tokens.

First chat run (2026-10-13): 1 failure in 100 turns, 0 leaks, 0 obeyed injections. The failure is `waterfall-weakness`, refused because its correct passage scores 0.48, under the 0.61 floor. Three unanswerable questions were answered (Kanban, JUnit assertions, a quiz question 4 that doesn't exist); each answer says the materials don't cover it.

## Outbox retry and broker recovery

Each outbox publishes due events in batches of up to 100, draining the backlog every second. A failed delivery is retried with backoff (doubling, at most five minutes apart) for 300 attempts, about a day. While events wait more than five minutes or have run out of attempts, the service logs an `outbox_backlog` error every minute, and each event that runs out logs `outbox_event_abandoned` with its id. Inspect only the affected service's `outbox` using its own database identity. Rows with `published_at IS NULL AND attempts >= 300` require operator action after repairing the broker. To retry a reviewed event, use a parameterized update on that specific event ID: set `attempts=0, next_attempt=now()` while retaining its original `id`, payload and creation time. Never invent a replacement grade or delete outbox history to clear an alert.

Consumers retry transient processing errors five times. On exhaustion they stop without committing the Kafka offset (logging `consumer_stopped_uncommitted`; Grading also reports not ready), and start again from the last committed offset after a backoff (5 seconds, doubling to a minute), so the event is retried once the dependency is repaired, with no restart needed. A `consumer_restarting` log line marks each wait. Invalid messages go to the consumed topic's dead-letter topic: `assessment.submitted.v1.dlq`, `assessment.submitted.v2.dlq`, `grading.finalized.v1.dlq`, `grading.finalized.v2.dlq` or `identity.classroom.deleted.v1.dlq`. Dead-letter content is confidential. Correct the source/contract issue, then replay only reviewed records. Preserve original event IDs. Analytics also protects against a new ID for an already processed evaluation.

Kong's OSS JWT plugin uses Keycloak's provisioned public key. Following a planned signing-key rotation, rerun `docker compose run --rm gateway-config`, then restart Kong. Backends use JWKS refresh. For production, automate overlapping-key provisioning before retiring a key; the local single-key setup is not a complete zero-downtime rotation system.

## Rebuilding analytics

Kafka's local retention is 30 days. Within retention, rebuild into a **new empty Analytics database owned by the Analytics role**: point Analytics' `DATABASE_URL` at it and give it a consumer group that has never committed an offset, by setting `ANALYTICS_KAFKA_GROUP` in `.env` (Compose passes it to Analytics as `KAFKA_GROUP`; the default is `analytics-v1`), for example `ANALYTICS_KAFKA_GROUP=analytics-rebuild-2026-10`. A new group starts from the earliest retained event. Then `docker compose up -d analytics`. Validate counts against released grading records before switching traffic: Grading publishes `grading.finalized.v2` only when a grade is released (at finalization for an assessment that releases on finalization, at the release for a manual one), so Analytics holds released grades only, and finalized grades still awaiting a manual release are not expected there. Never reset offsets while retaining the same inbox if the goal is rebuilding missing evidence. Historical grades beyond retention require a durable event archive or an authenticated Grading reconciliation/export API; neither is implemented. Do not claim indefinite reconstruction from the current broker alone.

## Production boundary

Local Compose is a development deployment only. Before production: deploy HTTPS OIDC and application origins, managed Keycloak persistence/backups, Kafka TLS/SASL with topic-scoped producer/consumer ACLs, per-service broker credentials, certificate-verified Neon URLs, separate migration/runtime roles, managed secrets, retention/backup/restore tests, and a maintained S3 provider. Remove the local E2E password-grant client and test accounts. Pin image digests, update supported patch versions, and run vulnerability/license scanning.

The private agents require a standard OIDC client-credentials identity carrying `ai-client` and the expected audience/organization. No such privileged application role is granted to ordinary teacher/student users. Future agent workflow authorization must use delegated user authorization or a narrowly scoped token exchange, never arbitrary input identity fields.

## Limits and consistency

HTTP requests are bounded (15 s, except uploads, which get 5 minutes and are spooled to a temporary file rather than held in memory); database pools are capped; uploads are limited to 50 MiB for PDFs and 5 MiB for text; assessments allow 50 questions; synchronous HTTP authorization calls have five-second timeouts. Lists currently have fixed caps and need cursor pagination. Analytics reads all scoped evidence to summarize it; high-volume deployments need SQL aggregation/materialized read-model metrics. Kafka operations do not hold a chain of service calls. Identity unavailability fails resource authorization closed.

S3 and PostgreSQL cannot share a transaction. Content uploads the object, then commits metadata/outbox, with best-effort compensation on known failure. A process crash can leave an orphan object. Reconciliation and ambiguous-commit handling are remaining risks; production needs a staged upload/finalization saga and a reviewed orphan cleanup job. No automated destructive cleanup is implemented.
