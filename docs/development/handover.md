# Engineering handover

This is the current state of the system. Why each rule exists is in `docs/decisions/` (ADRs 0001–0022), how to run, upgrade and recover it is in `docs/development/operations.md`, and service boundaries and data ownership are in `docs/architecture/system.md`. Dated history lives in git and in the ADRs: when something changes, update the section it belongs to here, and keep only the latest run of each kind under Verification.

## Delivered architecture

The repository began empty. It contains exactly ten independent application services, their Dockerfiles and tests, an Angular client, and reproducible local Caddy edge / Kong OSS / Keycloak / Kafka / PostgreSQL (pgvector) / S3-compatible object storage (SeaweedFS) infrastructure.

- **Go:** Identity/Classroom, Curriculum, Content, Assessment and Grading. Transactional, explicitly authorized operations with bounded request handling and SQL transactions.
- **Python/FastAPI:** deterministic Analytics and the four AI applications: ai-core (inference, ingest, rerank), the question chatbot (ADR 0002), question generation (ADRs 0006, 0015, 0022) and performance interpretation (ADR 0014).
- **Angular 21**, strict TypeScript, for the browser. Shell, SQL and configuration are operational artifacts; there is no third backend language and no extra business service.

## Deployment layout

- The `edge` container (Caddy, `infra/edge/Caddyfile`) is the public entry. It ends TLS for `app.localhost` (the web app, and Kong under `/api` on the same origin) and `auth.localhost` (Keycloak). Kong (8000) and Keycloak (8081) are published on 127.0.0.1 for scripts and tests only; the web app is not published.
- Three networks: `edge` (edge, web, Kong, Keycloak), `app` (applications, Keycloak, Kong) and `data` (PostgreSQL, Kafka, SeaweedFS; `internal`). Only services that own data join `data`; question generation and performance interpretation cannot reach a database or the broker.
- Every container has CPU and memory limits; long-running ones restart without a retry cap.
- Keycloak runs in production mode on its own `keycloak` database. The one-shot `keycloak-migrate` moved older H2 realms into PostgreSQL keeping every user's id; the realm requires HTTPS except from private addresses. Upgrade and rollback: operations.md, "Edge, networks and Keycloak on PostgreSQL".

## Behaviour by area

### Identity and classrooms
- OIDC authorization code + PKCE. Services verify RS256, issuer, audience, expiry and organization; resource policy comes from Identity; identity headers confer nothing.
- An account is exactly one of an admin, a teacher or a student, and keeps the role it first registered with. A token with more than one is refused everywhere (403 `ROLE_CONFLICT`); `POST /v1/me` refuses a role change (409). Usernames and display names come from the token at each sign-in.
- School admins (ADR 0019) manage their organization under `/v1/admin/`:
  - `GET`/`POST /v1/admin/accounts` lists (`role`, search, `offset`, `limit` 1–50) and creates teacher and student accounts. Creation makes the Keycloak user through `identity-accounts` with the school's `org_id` and a temporary password answered once (`accounts.go`), and records the user before their first sign-in. Each creation marks its Keycloak user with a random `identity_request` attribute; when Keycloak's answer is lost or is a server error, Identity removes only the account carrying its own mark. The sign-in username is `<org_id>.<username>` (`signInName`), so usernames are unique per school; search matches names and the part of the username after the school's id. `POST /v1/admin/accounts/{id}/password` gives one of the school's teachers or students a new temporary password, answered once the same way: it recovers an account whose creation answer was lost, or a forgotten password.
  - `/v1/admin/classrooms` creates classrooms for one of the school's teachers, renames or reassigns them (`PATCH`) and deletes them. A reassignment's `identity.classroom.reassigned.v1` is stamped with the database's clock under the classroom's row lock (`platform.EmitAt`), so Grading, which keeps the newest by timestamp, follows them in commit order whichever Identity process made each.
  - `/v1/admin/classrooms/{id}/students`, `/student-ids` and `/enrollments` read the roster and every enrolled id, and enroll or remove students, by account id or by username (the whole sign-in username or the part after the school's id).
  - Teachers only list their classrooms and read rosters. Another school's classroom answers 404.
- `GET /v1/classrooms/{id}/students` is the teacher's roster by name, paged (`offset`, `limit` 1–500, default 50) with `total`; `GET /v1/classrooms/{id}/student-ids` is every enrolled student's id in the same order, which other services use to filter teacher lists. Unenrolling writes `identity.enrollment.removed.v1` and enrolling `identity.enrollment.added.v1`, both stamped with the database's clock; submissions and grades are kept and come back on re-enrolment, AI suggestions included (ADR 0010).
- Deleting a classroom sets `deleted_at`, removes its enrollments and writes `identity.classroom.deleted.v1`; every service purges its own data for it and remembers it (`purged_classrooms`) so late events are ignored. Not purged: ai-core's usage ledger and event copies still on Kafka until retention.
- Account deletion (ADR 0011): Profile tab, `DELETE /v1/me` soft-deletes, clears names, removes enrollments and writes `identity.user.deleted.v1`; a teacher who still owns a classroom gets 409 `OWNS_CLASSROOMS` and asks the admin to reassign or delete it; an admin gets 403 `ADMIN_ACCOUNT`. Assessment, Grading, Analytics and the chatbot purge the user's work and keep `deleted_users`. Identity removes the Keycloak user through the `identity-accounts` client (`signins.go`), retrying each user independently with backoff (migration 008), so users Keycloak keeps refusing don't hold back the rest. ai-core's ledger is kept.

### Curriculum (ADR 0007)
- One level, called topic: `GET/POST /v1/topics`, `GET/PATCH/DELETE /v1/topics/{id}` (delete archives), `POST /v1/topics/{id}/restore`, prerequisites (`GET/POST /v1/topics/{id}/prerequisites`, `DELETE .../{prerequisite}`) with serialized cycle detection that counts archived topics.
- `GET /v1/topics?archived=true` lists archived topics so old questions and evidence keep their names. The product never deletes a topic; only test cleanup does (`local_stack.delete_topics`).

### Content
- Authorized uploads of teaching material only (ADR 0009) into a restricted bucket, with SHA-256, original retrieval and UTF-8 text extraction. Older rubric and marking-scheme documents keep their type and stay teacher-only.
- PDFs up to 50 MiB are indexed asynchronously through ai-core (`index_jobs`, leased by two workers, 30-minute lease, backoff to `AI_UNAVAILABLE` after six attempts) into chunks with `vector(1536)` embeddings, figure crops and full-text indexes; `content.indexed.v1` goes out on success. `POST /v1/documents/{id}/reindex` for teachers.
- Native formats (ADR 0013, migration 006): Markdown (5 MiB), PPTX and DOCX (50 MiB) are read locally into heading-aware chunks through the same queue, caches and spend checks. Headings, native tables and PPTX speaker notes are kept; citations show slides or section paths, not page numbers. Office images, charts and SmartArt are not interpreted. Plain `.txt` is extraction-only. Existing documents are not reindexed automatically.
- `POST /v1/search`: classroom access through Identity, vector and keyword legs, RRF, rerank through ai-core with RRF fallback, related figures and tables. Students only ever get teaching material.
- `DELETE /v1/documents/{id}` (teacher) atomically removes the row, chunks and indexing job, writes `content.deleted.v1` and queues `object_cleanup_jobs`. A leased worker removes the object prefix after commit and retains failures for retry; classroom purges use the same queue (ADR 0012). An hourly sweep also removes bucket objects older than 6 hours that no row names, re-checking each under the document row's lock just before removal.
- `services/ai-core/pdf_structure_probe.py` is a standalone offline CLI for PDF structure research, not connected to the app (`docs/development/structure-aware-pdf-research.md`).

### Assessment (ADRs 0004, 0005, 0008, 0017)
- Up to 50 questions: multiple choice, numerical, short answer (accepted answers) and free response (rubric, optional model answer), points per question, optional marking points (`marking_scheme`, up to 5 passages; teacher-only), and optional `sources`/`origin: "generated"` from question generation.
- Drafts are edited with `PUT`, published with `POST /publish`. A published assessment stays fully editable until a student submits; then only title, due date and late policy change (`PATCH`, fields left out are kept). A replacement or a due-date change on a published assessment writes `assessment.due_changed.v1` and recomputes `late`.
- `DELETE` answers 409 `HAS_SUBMISSIONS` when anyone (enrolled or not) has submitted; `?with_submissions=true` deletes it with its submissions and writes `assessment.deleted.v1`. The teacher list returns `submissions` (enrolled students only) and `has_submissions` (anyone).
- Students: opening and due dates (a submission or autosave is re-checked under the lock against the opening as stored, 404 before it), late policy (accept and flag, or 409 `CLOSED`, re-checked under the lock for submissions and autosaves), autosaved answers, one submission each, an answer-key-free projection. Answers or saved work naming questions the teacher has since replaced get 409 `ASSESSMENT_CHANGED`. `GET /v1/assessments/{id}/submission` gives the submitting student their own answers, `submitted_at` and `late` (404 before they submit, 403 for teachers).
- Submissions go out as `assessment.submitted.v4`.
- Create and edit requests take only the contract's editable fields: a top-level `id`, `published_at`, `assigned`, `resit_of` or `assignees` is 422 (before ADR 0017 `id` and `published_at` were silently accepted). Only the server sets whether an assessment is assigned, its `resit_of` and its assignees.
- **Question bank** (ADR 0017, migration 006): one per teacher, up to 2,000 questions (409 `BANK_FULL`, counted under an exclusive per-teacher bank lock). `GET/POST /v1/bank/questions` (paged, newest change first; filters `topic_id`, `type`, `q`, `origin`; with `classroom_id` + `student_id`, `answered` per question and `exclude_answered`), `GET/PUT/DELETE /v1/bank/questions/{id}`, owner only (404 otherwise). A bank question is an assessment question without its id, `sources` or `marking_scheme`; a bank request carrying passages is 422. `POST` with `{assessment_id, question_id}` saves an assessment question, passages stripped, also from published and submitted assessments; 409 `ALREADY_IN_BANK` (with the bank id) or `ASSESSMENT_CHANGED`. Each assessment question can name its bank question in `question_bank_links`, a plain reference outside the question; a link to a deleted bank question is ignored. "Answered" spans all of the teacher's classrooms, including ones the student has left.
- **Resits**: `POST /v1/assessments/{id}/resits` makes a draft in the same classroom from a published assessment the teacher owns: 1–100 assigned students on the roster, 1–50 distinct questions copied from the original (with their passages) and then the bank. It copies the late and release policies, AI marking only if a teacher-marked question remains, and no dates. `PUT /v1/assessments/{id}/assignees` replaces a resit's list (not empty; a student who submitted can't be removed, 409 `HAS_SUBMISSIONS`; a removed student's saved answers are deleted; 409 `NOT_ASSIGNED` on an ordinary assessment). An assigned assessment is visible only to listed students on the roster: every student path answers an unlisted student as for an unopened assessment (404, left out of lists and counts). Students see `resit: true`; teacher summaries and progress gain `resit_of` and `assignee_count`. The original grade is never changed.
- Purges: a deleted teacher's bank, a deleted student's assignee rows; a classroom purge cascades to links and assignees and leaves the bank. Resit creation takes up to 101 shared advisory locks (100 students and the classroom); bank writes, assignee changes and resit creation make no HTTP call while holding a lock.

### Grading (ADRs 0004, 0016, 0020)
- Kafka-triggered deterministic draft grading with exact decimal arithmetic and inclusive tolerance. Unmatched short answers and free responses wait for the teacher (`needs_marking`), optionally with an AI suggestion from `marking_jobs` workers through ai-core as `grading-marker`, billed to the assessment's creator, checked against the rubric before storing. A ready suggestion's job then becomes a `review` job (migration 011): the marking critic (ADR 0020) marks the answer again blind (`marking.review`, same teacher, same checks) and code sets `suggestion.review` to `agreed`, `doubtful` (levels differ, low confidence, a new flag) or `not_reviewed`; `MARKING_CRITIC=off` turns it off. `/counts` adds `ready_doubtful`. The review page shows the second check, a "Check AI mark" chip, doubtful drafts first and a non-blocking warning in both finalize dialogs.
- Teacher review is mandatory; finalization writes the record and an audit entry atomically. `POST /v1/evaluations/finalize` `{assessment_id, reason?}` finalizes every enrolled student's fully marked draft in one transaction and returns `finalized` and `needs_marking`; `/counts` adds `ready`. `POST /v1/evaluations/{id}/reopen` (required 1–1000 character reason) makes a finalized grade a draft at its next `revision` with an audit entry; the student no longer sees it until it is finalized again, and a released one writes `grading.reopened.v1`. The review page has "Reopen to correct" and "Finalize all fully marked", both behind confirmation dialogs.
- `grading.finalized.v3` (optional `revision`, absent = 1) goes out when the grade is released (at finalization, or at `POST /v1/evaluations/release` for manual release), so Analytics only ever holds released grades. Students see only their own released results (`GET /v1/evaluations/mine`, the newest 100; `/mine/page` pages them with `total`).
- Marking or finalizing a grade by id also needs its student on the roster (409 `STUDENT_REMOVED` otherwise); reading it does not.
- Teacher lists and counts include only students on Identity's roster (`platform.ClassroomRoster`, complete however large the class). A marking job for a removed student ends `STUDENT_REMOVED` without a model call, unless a newer enrolment of theirs has been recorded (`enrollment_returns`, migration 010); recording one queues those `STUDENT_REMOVED` suggestions again (`requeueRemoved`). `GET /v1/evaluations` is paged (`offset`, `limit` 1–100, default 20) with `total`; `GET /v1/evaluations/{id}` reads one grade for the teacher; `/counts` takes an optional `assessment_id`; a release releases only currently enrolled students' grades (ADR 0010).

### Analytics
- Keeps the newest released revision of each grade's evidence, with a `withdrawn` flag for a reopened grade until it is finalized again (migration 007), so an older, repeated or out-of-order event changes nothing. Each evaluation row names its assessment, classroom and student (migration 008, indexed, filled from evidence for older rows), so purges also remove withdrawn grades, which hold no evidence; a withdrawn row stored before migration 008 names none and is not purged. From 008 on, a row without them is refused with a retryable error (trigger `evaluations_owned`; migration 013 installs it where 008 ran without it), so a replica still on older code during a rolling upgrade leaves its event, uncommitted, for one that names them instead of storing a row no purge finds. Deploy Analytics before or with Grading when event versions change.
- Turns evidence into per-topic accuracy, attempted/correct counts, part marks and an explicit insufficient-evidence status; no mastery-probability claim. `weakness_indicator` ("Needs practice") is under 60% of the marks (part marks included) on the topic's latest ten questions, with at least five; `recent_attempted` and `recent_marks_accuracy` report those latest questions.
- `GET /v1/performance?classroom_id=` pages the current roster (from Identity with the teacher's token). The consumer group comes from `KAFKA_GROUP` (operations.md, "Rebuilding analytics").

### AI applications
- **ai-core** (private, `ai-client` role): `/v1/ingest` (local PyMuPDF text/layout extraction, selective vision for uncertain graphics/tables/OCR, configurable chunks; 500 pages / 5000 chunks max, `TOO_LARGE`), `/v1/inference`, `/v1/rerank`. Versioned operational caches reuse prepared PDFs and exact embedding inputs. Sorted per-input locks coalesce overlapping embedding batches within one process; provider calls retain existing billing and reservations. Every call names the billed user; PostgreSQL reservations enforce the allowance before each provider attempt and share `AI_USER_CONCURRENCY` (10) across replicas (ADR 0012). Actual usage settles reservations; uncertain or failed accounting conservatively retains them. Non-streamed `generate` takes an optional `timeout` that caps the generation budget, so a reply the caller stopped waiting for is not finished and billed; a structured reply that runs out of time is 504 `AI_TIMEOUT` (still charged). Tokenizer data is committed for both ai-core and the chatbot, with no runtime download.
- **Question chatbot** (`/api/chatbot`, own `chatbot` database): skips rewriting simple standalone definitions; retains rewriting for history, ambiguity and multiple topics (`query_rewrite.v3`). Searches the primary query first and adds searches for uncovered topics; passages under `TOPIC_FLOOR` (0.5) never reach the model, and the global relevance floor is 0.61. Evidence fits `CONTEXT_TOKENS` (8000 default) or the turn refuses without an answer call. After streaming, a local check adds a notice when a requested topic has no cited passage. Content receives the user's own token. Answers stream with citations and are always saved (`interrupted` on disconnect); a malformed stream event is `AI_PROVIDER_FAILED`. Citations of deleted materials are blanked (`removed: true`).
- **Question generation** (`/api/question-generation`, stateless): `POST /v1/questions` and `POST /v1/marking-guidance` for teachers; drafts must cite given passages and quote evidence found in them, and passages under `RELEVANCE_FLOOR` (0.5) are dropped. `model_calls` counts workflow inference requests attempted, including failed/refused attempts, rather than successful replies or provider charges. Content passage fields are validated locally before prompting. A reviewer pass (ADR 0015) checks each draft against only its cited passages and sends failures back with the reason, up to two retries within `QUESTION_REVIEW_DEADLINE`; counts are per question type, and a teacher can skip the review per request.
- **Student practice** (same service and Kong route, stateless, ADR 0022): `POST /v1/practice` for a student enrolled in the classroom: 1–10 whole teaching materials, an optional topic and focus (with neither, the query is the documents' titles from Content's list), multiple choice and short answer only, billed to the student under `practice.generated`/`practice.reviewed`. The review always runs and fails closed: only passed drafts are returned, flagged and unreviewed ones are counted in `dropped`, a set the reviewer never judged answers `503 REVIEW_UNAVAILABLE` (not `422 GENERATION_REJECTED`), and with `QUESTION_REVIEW` off the route answers `503 AI_UNAVAILABLE`. Content's list is paged with a 10-document overlap, so deletions between page reads do not hide a chosen title. The page says how many of the questions asked for are missing (`requested - returned`), not the per-draft `dropped` total, and asks before a new set replaces answers still to check. Keys, explanations and sources come back with the set; the Practice page (Learn) reveals each only after the student checks their answer. Nothing is saved or graded.
- **Performance interpretation** (`/api/performance-agent`, stateless): `POST /v1/performance_interpretation` for a classroom's teacher and one enrolled student. It pages Grading (up to five pages of 100) until it has the newest 20 finalized results. A bounded tool loop (`PERFORMANCE_MAX_TURNS` 5, `PERFORMANCE_DEADLINE` 120 s) over Analytics, Grading, Assessment and Curriculum; each turn lists the question references a report may cite, the topics it may recommend and the `suggested_checks` (prerequisite and class checks) not yet made. The absolute budget includes authorization and opening reads; topic names use Curriculum batches of up to 50 ids. Class comparisons retain the 200-student roster-order limit and expose population, compared count and partial scope to the model and teacher. Service-local upstream views validate metrics, finalized evidence, question snapshots and topic names at client boundaries. Findings cite only questions it was shown, misconceptions only answers it read that lost marks (ADR 0014). A tool turn that is unreadable or fails goes straight to the report, counted in `dropped`.
- **Class insights** (same service and Kong route, stateless, ADR 0021): `POST /v1/class_insights` for a classroom's teacher takes a question (1–500 characters) and up to three earlier questions, which reach the model as context only. It runs on the interpretation agent's turn loop, now in the service's `loop.py` with the same turn, deadline and budget settings. It opens with Analytics' class metrics (first 200 students in roster order, with population, compared count and partial flag), Identity's roster names (up to 500, kept in the agent) and Curriculum's topic names. A class with no released evidence answers `422 NO_EVIDENCE` without a model call. The tools are `topic_detail`, `topic_questions` (one shared read of the class's finalized evaluations, up to five pages of 100), `student_results` (only students the class figures cover), `read_answers` (a class question or one student's result) and `prerequisites`; `topic_questions` and `student_results` say `older_results_not_read` when older evaluations, finalized or drafts, were left unread. The model sees `S1`/`T1`/`Q1`/`R1`/`E1` references only, and names are added after the checks for the cited students. A text is dropped as `REFERENCE_IN_TEXT` only for a reference the agent gave out, and the step trace shows names: targets are names or titles, and references in the model's step reasons (in both agents) are replaced with words. A struggling student must have enough released evidence on the topic (`observed`) and either the needs-practice flag or under 60% of the marks. A misconception cites only read answers that lost marks. When nothing survives, the answer is `422 INSIGHTS_REJECTED`, or `422 NOTHING_TO_ANSWER` when the model reported nothing at all. The response's `evidence_ids` are the answers' `E` references, local to that response.
- The agents share their ai-core and Content transport in `learning_transport`, which passes ai-core a `timeout` `REPLY_MARGIN` (5 s) under the agent's own deadline. Planned agentic work: `docs/architecture/agentic-workflows.md`.

### Web
- School admins land on `/admin/classrooms` in their own shell: Classrooms (create with a teacher, edit, delete, and enroll or remove students), Accounts (create with a temporary password shown once; list by role; reset a password, after a confirmation) and Monitoring. Teachers land on the Class dashboard, students on Home. Sections: Classrooms and Students (teacher, read-only), Curriculum (teacher), Materials with indexing status and delete, Ask the materials (streamed chat with sources), Assessments (list, editor and preview with a generation side panel; student full-page taking with autosave), Question bank (teacher), Grading review (queue with grade panel and next-to-mark navigation, inline marking, AI suggestions), My results, Learning performance / My progress, Practice (student, ADR 0022), Profile.
- Class insights (ADR 0021): the Class dashboard's "Ask about this class" panel (`features/dashboard/class-insights.*`) posts one question with up to three earlier ones, locks the classroom while it runs, links cited students to Learning performance, and shows `NO_EVIDENCE`, `NOTHING_TO_ANSWER` and `INSIGHTS_REJECTED` as empty states; it keeps no saved threads.
- Practice (ADR 0022): `features/practice/practice.*`, student-only under Learn, ticks indexed teaching materials (the filter `shared/generation.ts` shares with the generator), posts `/v1/practice`, locks the classroom while it runs, and keeps the set in the tab only. Each question's key, explanation and passages show only after "Check answer"; short answers match after folding case, spaces and punctuation, and a miss shows the accepted answers to compare. "More questions" sends the prompts shown as `existing_prompts`.
- Every list loads through `shared/section.ts` and shows loading, empty and failure states; evidence names use targeted batches of up to 50 ids in `CurriculumNames`, retaining at most 512 recent names/misses per user; dialogs use `app-confirm-dialog`. The app reads its gateway and Keycloak URLs from nginx's `/config.json`.
- Classroom/topic/document/assessment APIs expose additive `/page` endpoints (`offset`, `limit` 1–100, default 20, `{items,total}`); legacy array endpoints retain their old caps. Materials and assessments use `PagedSection`; explicit native pickers still read complete option lists in server pages; evidence labels no longer trigger those full reads. Progress uses `/progress/page`; assessment detail reads coalesce into authorized batches of up to 50. Class dashboard roster reads only its visible page plus the total.
- Question bank and resits (ADR 0017): `/question-bank` lists, filters, writes, edits and deletes the teacher's bank questions. The editor's side panel has "Add from bank" beside generation; each question has "Save to bank" (or "Update bank copy" and "Save as new" once linked), disabled with a note while the form has unsaved changes, and the form round-trips each question's `bank_question_id`. "Create resit" on a published assessment in the list and in Grading review opens the builder at `/assessments?resit=<id>`: its roster reads twenty students per page and keeps up to 100 chosen names across pages, with removal controls; it suggests students on viewed pages who lost marks on finalized grades (up to five pages of 100, saying so when more remain) and bank questions on those topics with answered ones hidden, copies chosen questions from the original, and opens the new draft in the editor. Resits carry a "Resit" label for teachers and students, and the class dashboard counts submissions out of `assignee_count`. There is no screen yet for changing a resit's students after it is created (the API and client exist), and no entry from Learning performance.

Grade queue selection and navigation live in `features/review/grade-queue.ts`, independently of marking actions. Assessment resit/assignee handlers live in `resit_handlers.go`, separately from question-bank CRUD.

## Events and persistence

- **Current topics:** `content.uploaded.v1`, `content.indexed.v1` (no consumer), `content.deleted.v1`, `assessment.submitted.v4`, `assessment.deleted.v1`, `assessment.due_changed.v1`, `grading.finalized.v3`, `grading.reopened.v1`, `identity.classroom.deleted.v1`, `identity.classroom.reassigned.v1`, `identity.enrollment.added.v1`, `identity.enrollment.removed.v1`, `identity.user.deleted.v1`. Older versions were retired on 2026-10-19 (ADR 0007 amendment). Consumed topics have `.dlq` topics; `kafka-init` creates them all and sets 7-day retention on submission, finalized-grade and dead-letter topics.
- Producers write outboxes in the business transaction and publish at least once; only the oldest unpublished event per topic and key is due, so keys stay ordered, and each relay publishes batch after batch until nothing is due (for up to a second a tick), so a key's later events follow at once. Outboxes prune every event published over 7 days ago, 1000 per statement, in a minute loop of their own, so a long prune never delays publishing; each batch reads through the partial index `outbox_published` (`platform.OutboxIndexes`), which every service with an outbox builds, Identity included. Purges delete their outbox events through partial expression indexes on `classroom_id`, `assessment_id` and `student_id`, built concurrently by Assessment, Content and Grading beside publishing (`platform.IndexBuilder`, one replica at a time, retried after a failure); until a build finishes, prunes and purges scan the outbox. The purge keys are `platform.PurgeByClassroom`, `PurgeByAssessment` and `PurgeByStudent`: a purge by any other field does not compile. `platform.EventMigration` is applied once per text (recorded by digest in `schema_bootstraps`), so a restart runs none of its DDL. Grading builds `evaluations(classroom_id, student_id)`, `evaluations(student_id)` and `audit(evaluation_id)` the same way for returns, account purges and the audit foreign key; Content builds only its `classroom_id` index. Analytics applies each migration on its own (`open_migrated_pool`), so its owner-column backfill and indexes never hold a table lock that blocks reads. Consumers commit offsets only after the inbox/business transaction or a confirmed dead-letter write; event-ID plus business-key deduplication covers replays.
- Nine service-owned databases (eight application databases plus Keycloak's; question generation and performance interpretation are stateless) with independent non-superuser credentials. All advisory locks use `platform.Lock`/`learning_transport.db.lock` (`hashtextextended(scope || ':' || key, 0)`).

## Operational notes

- School admins use `/admin/monitoring` for service readiness, five-minute response-header p95, Kafka dead-letter estimates and their own school's ai-core expenditure (ADR 0019). Provisioning and metric meanings are in operations.md, "Platform monitoring".

- Kong re-resolves service names every 5 seconds; a new route still needs `docker compose restart kong`.
- Kong rate-limits per `Authorization` header (120 a minute per signed-in session).
- Stop every replica of a service before starting a version that changes lock ids.
- Upgrading an existing `.env` or stack: `python scripts/upgrade_local.py` (adds missing values, databases and Keycloak clients, idempotent), then `docker compose up -d --build`. Trust the edge's local certificate authority once (README).
- The owner's $5 aggregate cap covers all paid work; preserve development and test usage ledgers and check remaining allowance before paid runs.

## Incomplete requirements and risks

The full requested definition of done is **not claimed**. The core workflow is implemented, but these remain incomplete or narrower than the brief:

- Numerical generated questions. Student practice (ADR 0022) saves nothing, offers no free response or page ranges, and is not targeted at weak topics. Each student can submit an assessment once; a second attempt is a resit (ADR 0017). Filling bank gaps with question generation and the adaptive resit agent (agentic workflow 4) are not built, nor sharing banks between teachers or "best of" grades.
- Document revisions beyond revision 1 and lesson-plan persistence. Performance interpretations are drafts on request: none run on finalization or are saved.
- Assessment trends, richer teacher summaries, and archival/reconciliation beyond Kafka's 7-day retention.
- Offset pagination can drift under concurrent insertions; metadata pickers still accumulate their full authorized list. Cursor pagination and server-side picker search remain future work.
- PDF figure/table kind failures (Basic Security p16, Automation and Deployment p9) need extraction work and reindexing.
- Production: real certificates instead of the edge's local CA, Kafka TLS/SASL/ACLs, per-service machine identities, Keycloak database backups, signing-key rollover, separate migration/runtime roles, backups/restore testing, secret management and dependency/image audits.
- Assessment does not consume `content.deleted.v1`, so source passages and marking points of a deleted material stay in assessment questions, and in resits copied from them. They are teacher-only; the bank holds no passages, so it does not widen this.
- A resit holds up to 101 shared advisory locks (100 students and the classroom). PostgreSQL's lock table holds `max_locks_per_transaction` (64) × `max_connections`, so raising the 100-student cap or running many large resits at once needs that budget checked (operations.md).
- S3/SQL atomicity relies on retaining ambiguous originals plus the hourly sweep, not a staged-upload saga.
- Reservation estimates depend on configured model prices and image/token allowances. Uncertain provider outcomes or ledger-write failures retain conservative holds; operators must investigate these instead of blindly releasing them.
- Static checks and focused browser tests are not a comprehensive accessibility, multi-browser, load, chaos or security assessment.

Recommended next: a screen for changing a resit's students, practice targeted at weak topics, filling bank gaps with question generation and the adaptive resit agent, interpretation on finalization, cursor pagination, and the next agentic workflows in `docs/architecture/agentic-workflows.md`, each behind its own ADR as AGENTS.md requires. Preserve teacher approval and evidence provenance throughout.
